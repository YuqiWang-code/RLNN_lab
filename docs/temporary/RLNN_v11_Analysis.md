## 0. 五条结论（先看这个）

1. **门 0 过了，S1 不可评，S2 只能落「R 进 Discussion」。** 门 0 (i) 8/8 全 true、search 20.069、Δ=0.0、artifact 四列一致；
   但本轮**没有任何 C3 干预臂**（A1/A1′/A2/A2′ 已按 §14.10 剔除、A4 未跑），S1 的必达项无从评；
   S2 三命题里 P1 过、P2 差 0.0073 未达标、P3 未测 ⇒ 按 §14.2 的门只能取「只有 P1 过」这一局面。
2. **1 s 档没用满预算：A0 只花掉 0.745 s。** 搜索步耗时 0.877 ms/步 × 810 步 = 0.711 s，
   加 decode/load 后 `solve_time_s` 0.7449（= 1.0 s 预算的 74%）；同一时钟下跑 1079.8 步的时钟臂用掉 0.986 s 得 final 20.0785 / search 20.077（产物 `a0_clock1s_n1000/`，门 0 只把它当报告项）
   ⇒ **1 s 预算里还留着约 +0.009 没取**，与 RLSA 的 −0.015 差距有一半以上是「固定 808 步」这个决定造成的，不是能力差距。
3. **0.2 s 档落后的 0.076 全部是吞吐，不是搜索质量。** 0.2 s 档每步 1.288 ms（1 s 档 0.877 ms，贵 46.8%），
   只能跑 126.1 步；按步数曲线（更贵的每步外推）126→230 步对应 19.889→≈19.983。**步数够了就追平，问题在每步成本。**
4. **训练侧不是当前瓶颈但确实欠训。** ref0 只有 3 epoch（val 19.53 在 ep2 触顶后回落到 19.50）；50 epoch 基线 val 峰 19.56@ep43、
   末轮 19.47 ⇒ 训练侧理论上限约 +0.03（vs ref0 19.53），需要 100k 更新才拿到，**性价比低于第 1 条**。
5. **口径风险（会被审稿人抓）**：README 的 0.2 s 招牌数 **19.8410** 来自 `outputs/v8_macro/padded_short/`（1000 图单 seed 1017、414 步、0.384 ms/步；该 run 的
   `padded_ref0.json` 不含 dtype/K 字段，但 414 步/0.384 ms 与 A0 的 126 步/1.288 ms **互斥** ⇒ 必是不同构建），**与 A0（fp16+dense、K=200、0.2 s 只跑 126 步 = 19.886）不是同一构建**。
   「1 s 20.069 + 0.2 s 19.841 两档同时改善」这句话混用了两套构建，对外必须拆开说。

## 3. 机制归因（闸门 + 探针说话）与失败模式分类

### 3.1 门 0 / 闸门说了什么（`gates_gate0.json`、`gates_selftest.json`、`audit_dense_csr.json`）

- 门 0 (i)：passed=true，checks 8/8；reference 20.069（`reference_kind = A0_declared_config_fp16_dense_810_steps`）、delta_search 0.0、
  `artifact = {dtype fp16, dense 1, fp32_csr 0, fixed_steps 808, steps 810, consistent true}`；config_sensitivity 0.007。
- 自测 10/10（含 `same_seed_bitwise`、`frozen_equivalence` 3 图 × 2 seed 六项逐位相同）⇒ **同 seed 可重复性成立**。
- `audit_dense_csr.json`：26 张「我的解 ≠ 基线码」的图上，dense/csr 与 mine 100% 一致（26/26、26/26），对 baseline 0 命中；
  8 张对照图四方全 20.375（8/8）⇒ **flip 不是 dense/csr 转换带来的**，是 baseline 码路径 vs 现行码路径的语义差。
- 结论：闸门层面**没有**发现引擎漂移。0.007–0.008 是 fp32↔fp16 **配置敏感度**（数值路径差，确定性、可通过声明配置避免），
  不是抖动、也不是可平均掉的噪声；因此**不可用旧 artifact 的 fp32 值做对照**。

### 3.2 四类失败模式，逐类给证据

| 类别 | 判定 | 数字 |
| --- | --- | --- |
| **吞吐（throughput）** | **主因，两个预算档都是** | `ms_per_step` 是「搜索步耗时/步」：0.2 s 档 **1.288** vs 1 s 档 **0.877**（+46.8%），同样 126 步要多付 (1.288−0.877)×126 ≈ **52 ms = 0.2 s 预算的 26%**；再加 decode+load ≈25 ms（solve 187 − search 162）⇒ 0.2 s 档 187 ms 里只有 162 ms 真在搜索。1 s 档固定 810 步只用掉 0.745 s（余 26% 预算）。0.1 s 档 21.6 步、`ms_per_step` 9.65（把捕获/prelude 摊进了每步）、solve 0.0929 s ⇒ **伪档，不可用于斜率外推**（同 §14.2 对 0.05 s 档的处理） |
| **表达力（expressiveness）** | **在「一步前瞻 + 极大集」族内已顶住，不是本轮失败点** | 步数曲线 130→19.889 / 200→19.970 / 280→20.004 / 350→20.027 / 450→20.044 / 810→20.069，边际 +0.1157→+0.0069（每 100 步递减）；M4 精确 k≤6 邻域 0/648；C4 逃逸 deploy:h0 与 h=8 的 gain 均 **0.0000**（200 图，`t7/escape/`） |

| **采样（sampling）** | **不是瓶颈，但换来一个新的不可重复性来源** | 0 步图 0 张、deadline_overrun 3/1000、同 seed 逐位可重复；但时钟限时把随机性从模型搬到了调度：0.2 s 步数 CV 0.16（126.1 ± 20.2）、1 s 固定步数 CV 0.0 |

### 3.3 归因链（把差距拆到可行动的项上）

- **对 RLSA（1 s）落后 0.015**：配置敏感度项 0.007（fp32↔fp16 数值路径差，确定性、可避免）+ 未用满预算项 **0.009**
  （固定 808 步 → 时钟 1079.8 步）+ 残余 ≈0。⇒ 其中 0.009 是零成本可回收项（详见 §6）。
- **对 RLSA（0.2 s）落后 0.076**：步数项 126 → 230（把每步成本压到 1 s 档水平即得）⇒ 19.889 → ≈19.983（+0.094），**覆盖 0.076 还多**。
  所以 0.2 s 档的问题不是「K=200 太贵装不下」，而是「短时域每步贵 46.8%」。
- **训练项**：ref0 19.53 vs 50 epoch 峰 19.56（+0.03）⇒ 训练侧最多值 +0.03，且要 100k 更新（5982.9 s ≈ 1.66 h GPU）。

## 5. 三条建议（按性价比排序）

### 5.1 【先做，零新增 GPU】把 1 s 档从「固定 808 步」改成「用满预算」，参考值重新声明
- 依据：clock 臂 1079.8 步 = final **20.0785** / search **20.077**，A0 810 步 = 20.069/20.0705；同一批图 0 胜 / 992 平 / 8 负（A0 − clock = −0.008，CI [−0.014, −0.003]）。
- 预期收益：**+0.0085**（把对 RLSA 的 −0.015 改写为同墙钟 −0.006，跨过一个配置敏感度量级）。
- 最小验证成本：**~25 min GPU**（1000 图 × 1.0 s，已有同一脚本 `train_scripts/v11/a0_gate0.sh` 的时钟分支），或直接复用 `a0_clock1s_n1000`（已存在，只需在门 0 里把它从「只报告」升为主参考并重定基）。
- 风险：换参考值等于重开判据口径，必须由 captain 在锁定文档里写一条新台账（否则 §0.5 的 Δ 基准漂移）。

### 5.2 【解锁 S2 判决】补 0.3 s「多 0.1 s 搜索」对照臂 + P3 回归
- 依据：P2 现在「主项差 0.0073 + 对照项未测」，P3 完全未测 ⇒ S2 只能落 Discussion（§14.2）。这是**判据缺项**，不是能力缺项。
- 预期收益：把 S2 从「不可评」变「可判」。若 0.3 s 对照低于 0.2 s+PAVE，P2 主项就能按 +0.0227 判「有信号但未达 +0.03」；若反过来，P2 直接判死。
- 最小验证成本：0.3 s 档 1000 图 × 3 seed ≈ **15 min GPU**（0.2 s 档 3 seed 墙钟 ≈190 s/档）；P3 的 stats→C 回归**纯 CPU、≤1 min**（`outputs/v11/p1_law_1000.json` 已有 5 档 × 1000 图的 `mean_c`/`mean_rho`，逐图 CSV 在服务器）。

### 5.3 【唯一能补质量的路】拆 0.2 s 档的每步成本（1.288 → 0.877）
- 依据：0.2 s 档 `ms_per_step` 1.288 vs 1 s 档 0.877（+46.8%）⇒ 126 步多付 52 ms（26% 预算）；0.2 s 档墙钟 187 ms = search 162 + decode/load 25。
  t8 另估「~43 ms/图不在固定项内」（sync / 超时判定 / decode 节奏），本轮未能从现有列切出来（CSV 无 sync 列）⇒ 需打点。
- 预期收益：步数 126 → 230 时 0.2 s 档 19.889 → ≈19.983（**+0.094**，覆盖对 RLSA 的 −0.076），并顺带把步数 CV 从 0.16 压下来（0.2 s 档三 seed 稳健性恢复）。
- 最小验证成本：**CPU 侧 30 min 拆解**（在 `models/mis_v8_pad.py` 的 `PaddedSearch.run()` 打 6 个分段计时：capture/load/prelude/search/decode/sync，100 图各一次）+ **200 s GPU** 重跑 1000 图 × 0.2 s 验证。
- 注意：这是「吞吐」路，不是「表达力」路；按 §0.6 + §14.3 + §14.10.9，表达力侧（更大邻域、记忆、多步目标）已有三条独立负结果，不值得再投入。

## 6. 「1 s 用满预算」——协议口径问题，不是算法问题

| 口径 | 步数 | search | final | 用掉的 1 s 预算 |
| --- | --- | --- | --- | --- |
| A0（`--fixed_steps 808`，为与历史 20.0685 对齐） | 810.0 ± 0.0 | 20.069 | 20.0705 | solve **0.7449 s = 74.5%**（search 部分 0.711 s） |
| clock 臂（deadline 口径，同一批 1000 图） | 1079.8 ± 14.7 | 20.077 | 20.0785 | solve **0.9857 s = 98.6%** |

- **白扔 +0.0085**（final 20.0785 vs 20.0705）：逐图 0 胜 / 992 平 / 8 负，A0 − clock = −0.008 [−0.014, −0.003] 不含 0（`tmp/t10_stats.json` `paired_cells`）。
- **为什么是口径问题**：810 步的唯一理由是钉住历史参考（`gates_gate0.json` `reference_kind = A0_declared_config_fp16_dense_810_steps`），
  而对外比较用的是**同墙钟**、不是同步数 ⇒ **步数容量 75.0% 已用、25.0% 未用**（810/1079.8）；
  solve 时间口径同结论（**74.5% 已用**，0.7449/1.0）——两基同一结论、不混用。换 deadline 口径是零成本回收。
- **对 RLSA 的差距应改写**：**同墙钟 −0.006**（20.0785 vs ≈20.084），其中 **0.007 是 fp32↔fp16 配置敏感度**（确定性、可避免）；
  旧写法「落后 0.015」混入了 0.009 的固定步数损失。
- **风险三条**：①1079.8 步 × 0.878 ms = 948 ms，solve 0.9857 只剩 **14.3 ms（1.4%）余量**，步数抖动 ±14.7 步（≈±13 ms）会吃掉它
  ⇒ 换口径必须留 **≥15 ms reserve**（captain 已写进 L1/L2 判据：新口径不留 15 ms，分数会随机器抖动）；②参考值必须重定基（20.069 → 20.077），需 captain 在锁定文档写新台账，否则 §0.5 的 Δ 基准漂移；
  ③0.2 s 档不同理——那一档的瓶颈是每步成本 1.288 ms（§5.3），不是预算没用满。

**§6 定稿结论（captain 2026-11-18 定，照抄）**：
> 「1 s 档的 −0.015 全部可解释：0.007 配置敏感度 + 0.009 未用满预算 + 残余 ≈0；换 deadline 口径并留 15 ms reserve 后，同墙钟对 RLSA 为 −0.006（在配置敏感度内）。」
